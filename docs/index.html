Catch untrainable robot data before you burn GPU hours on it.

robolint is a quality checker for LeRobot datasets, local or on the Hugging Face Hub. Point it at a dataset and find out which episodes will quietly hurt your policy: dead episodes, stacked recordings, dropped frames, teleop glitches, frozen cameras, broken metadata.

Install the CLI See the audit of 18 datasets Try it in the browser

Free and open source. Built by Max McCutcheon.

Why

Bad robot data doesn't crash training. It just makes the policy worse.

Robot data is expensive to collect and easy to get subtly wrong. A follower arm unplugs mid-session and you record minutes of actions with no motion. USB bandwidth drops camera frames and video drifts out of sync with actions. A teleop glitch makes a joint jump 150° in one step. An episode is uploaded twice. Nobody notices. robolint tells you exactly which episodes to drop or fix.

What it checks

Five areas, every episode

Supports LeRobot v2.x (per-episode files) and v3.x (chunked files) layouts.

01

Timing

Dropped frames (timestamp gaps), timestamps going backwards, jitter, drift from declared fps, frame_index gaps and duplicates.

02

Actions & state

NaN/inf values, dead episodes (robot never moves), frozen state (follower disconnected), teleop glitches (action spikes), idle lead-in/tail padding, gripper never actuating, joints pinned at limits.

03

Episodes

False starts, truncated and runaway episodes, metadata/data length mismatches, near-duplicate episodes, missing or unknown tasks.

04 · --videos

Video

Missing or unreadable files, video/action length mismatches, black, blown-out, blank and frozen camera feeds, fps and resolution mismatches.

05

Metadata

Declared vs actual episode/frame counts, missing features, shape mismatches, vague task descriptions that can't condition a VLA policy.

Safety

Datasets are untrusted input

No pickle, no code execution, file paths from metadata are confined to the dataset folder, and every string in HTML reports is escaped.

How scoring works

Every episode gets a 0–100 score; the dataset gets a score and a letter grade (A ≥ 90, B ≥ 80, C ≥ 70, D ≥ 60). The dataset score is the average episode score, minus small penalties for dataset-level problems. Roughly: the share of your data you can actually train on.

error
Makes an episode unusable for training, so it scores 0.
warning
Each distinct warning costs 15 points.
info
Costs 2 points.

What's broken in public robot learning data

We ran robolint over 18 of the most-downloaded LeRobot datasets on the Hugging Face Hub to see how common these problems are. Every number is reproducible with the command-line tool.

  • 18public LeRobot datasets
  • 4,218episodes
  • ~2.7Mframes
  • 3 of 8community datasets we would not train on as published

The simulation benchmarks are clean. Real-robot teleoperation data is where things break, including in official reference datasets, and 3 of the 8 community datasets have structural problems serious enough that we would not train on them as published.

1Recordings stacked on top of each other

The most serious problem found. In two datasets, the data files contain two separate recordings under the same episode number: frame numbers restart halfway through the episode and timestamps jump backwards. A loader that indexes by episode will hand the policy two different demonstrations spliced together.

  • kmg0620/so101_bomb_pick_place_v1: metadata describes 103 episodes and 57,211 frames; the data holds 150 episodes and 88,782 frames, 55% more than declared.
  • EPITECH-LILLE/eval_training: info.json declares 0 episodes and 0 frames; the data holds 60 episodes and 41,686 frames, and episodes 0–19 each contain two recordings.

2Metadata that no longer describes the data

Tools that trust the metadata see the wrong dataset, or an empty one.

  • SO-101-robot-learning/so101_pick_place: info.json declares 0 episodes; the data holds 50 episodes and 17,870 frames.
  • jchandru08/so100_press_red_button: declares 19,028 frames, holds 17,156. Three episode numbers are missing and 7 episodes are off by 1–3 frames, so a metadata-built index points at slightly wrong frames.

3Dead and false-start episodes, including in official datasets

Almost always recordings started by accident. Each one teaches the policy that doing nothing is a valid demonstration.

  • lerobot/svla_so100_stacking: episode 20 is a single frame; episodes 37, 38, 39 and 55 never move.
  • lerobot/svla_so100_sorting: episodes 8 and 23 never move. Episode 23 is 51 frames, against a median of 694.

4Idle time

Operators start recording and wait, or forget to stop. Idle frames aren't wrong, but in large amounts they bias a policy toward hesitating. Trimming them is cheap.

  • Embodied-AI-6/dataset: 27,000 of 81,786 frames (33%) are the robot standing still; one episode is 57% idle.
  • lerobot/svla_so101_pickplace: 26 of 50 episodes are at least 15% idle (21% on average).

5Smaller issues

  • Empty task description, so the data can't condition a language-driven (VLA) policy.
  • A wrist pushed into its hard stop mid-task; a leader/follower calibration offset (usually harmless).
  • 22 of 1,445 episodes with a single-frame tracking jump: a very clean dataset for its size.
  • 5 near-identical scripted demos: expected, but worth knowing when counting effective dataset size.

✓What was clean

The simulation datasets (PushT, ALOHA sim, LIBERO with 1,693 episodes) came back essentially clean, as did the DAgger rollouts from recast-robotics (whose robot setup isn't documented). The problems concentrate in real-robot teleoperation data and in how datasets are assembled and uploaded.

How the audit was run

robolint checked timing, actions and state, and episode structure. Video was not checked in this audit. Every check is tested against synthetic datasets with injected faults, and the audit itself surfaced three false positives (sample-and-hold controllers, binary gripper commands, and an arm resting on its stop) that were fixed before these numbers were produced.

Reproduce it 
pip install "robolint[all] @ git+https://github.com/maxmccutcheon59/robolint.git"
robolint audit --from-file datasets.txt --out audit

datasets.txt lists the 18 datasets.

Caveats

Thresholds are judgment calls, so findings are a starting point for review, not a verdict. This is one snapshot of 18 datasets, not a survey of all robot data. If you maintain one of these datasets and think a finding is wrong, please open an issue.

Install & quickstart

From install to first report

Requires Python 3.10+. robolint installs from GitHub (it isn't on PyPI yet).

Install everything (Hub downloads + camera checks) 
pip install "robolint[all] @ git+https://github.com/maxmccutcheon59/robolint.git"
  • robolintlocal datasets
  • robolint[hub]Hub downloads
  • robolint[video]camera checks
  • robolint[all]everything
Check a dataset 
# Local folder or Hub repo id
robolint check ./my_dataset
robolint check your-org/your-dataset --videos

# Shareable reports
robolint check your-org/your-dataset --json report.json --html report.html
Drop bad episodes before training 
robolint check your-org/your-dataset --exclude-out bad_episodes.txt
robolint check your-org/your-dataset --exclude-out flagged.txt --exclude-level warning
Gate a data pipeline in CI 
robolint check ./my_dataset --fail-under 85
Spot-check a huge dataset (first N episodes only) 
robolint check cadene/droid_1.0.1 --max-episodes 200
Audit many datasets at once 
robolint audit lerobot/pusht lerobot/svla_so101_pickplace --out audit/
robolint audit --from-file datasets.txt --out audit/
From Python 
from robolint import lint

result = lint("lerobot/pusht")
print(result.scores.dataset_score, result.scores.grade)
for f in result.findings:
    print(f.episode, f.severity.label, f.code, f.message)

Exit codes

0 success · 1 score below --fail-under · 2 dataset could not be loaded

Other flags: --revision (Hub branch, tag, or commit), --cache-dir, --no-color. Run robolint check --help for the full list.
